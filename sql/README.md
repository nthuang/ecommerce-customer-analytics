# PostgreSQL models

These scripts load the source CSVs into a `raw` schema and create three analytics views:

- `analytics.order_fact`: one row per delivered order. Items, payments, and reviews are reduced to order grain before joining.
- `analytics.customer_features`: one row per `customer_unique_id`, with RFM-style recency, frequency, monetary value, average order value, and repeat-customer status.
- `analytics.seller_performance`: one row per seller with delivered seller-order counts, item revenue and freight, delivery timing, and review measures.

The latest review for an order is selected by review creation date, then answer timestamp, with `review_id` as a final tie-breaker. `review_id` is not unique in this dataset, so the raw review table uses a generated row key instead.

Seller delivery and review metrics are calculated from one row per seller-order after aggregating that seller's items. Delivery-versus-estimate uses calendar days (positive means late); the late rate uses rows with delivery and estimate dates. The low-review rate is the share of reviewed seller-order rows scoring 1 or 2. When an order contains multiple sellers, its latest order-level review is associated with each seller; these review metrics are descriptive and are not seller-specific causal ratings.

## Load and build

Configure `DATABASE_URL` in your local shell to point to a dedicated project database. Do not commit credentials. Run these commands from the repository root; the load script uses relative paths and should be run once against empty project tables.

```bash
psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f sql/00_load_raw.psql
psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f sql/01_order_fact.sql
psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f sql/02_customer_features.sql
psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f sql/03_seller_performance.sql
psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f sql/04_export_powerbi.psql
```

The export script writes `data/processed/powerbi_order_fact.csv` and `data/processed/powerbi_seller_performance.csv` for Power BI. Run it from the repository root after building the views. The customer-segment CSV is generated by `notebooks/customer_features.ipynb`.

## Validate

The order and customer views were validated against the pandas exports; seller aggregates were reconciled with `analytics.order_fact`:

- `analytics.order_fact` contains 96,478 unique orders and item revenue of 13,221,498.11.
- `analytics.customer_features` contains 93,358 unique customers and 2,801 repeat customers.
- Order-level measures and customer counts, revenue, average order value, freight, recency, state, and repeat flags reconcile with the pandas outputs. SQL first/last order fields use calendar-date precision.
- One delivered order has no payment row and 646 have no review; the left joins preserve these as `NULL` rather than dropping the orders or inventing values.
- `analytics.seller_performance` contains 2,970 sellers and 97,819 seller-order rows. Its 110,197 items, item revenue of 13,221,498.11, and freight of 2,198,275.64 reconcile with `analytics.order_fact`.
- Eight seller-order rows have no delivery timestamp and are excluded from delivery-time averages. Seller review counts are seller-order observations, so a review can count for more than one seller when an order contains multiple sellers.

```sql
SELECT
    COUNT(*) AS rows,
    COUNT(DISTINCT order_id) AS unique_orders,
    SUM(item_revenue) AS item_revenue
FROM analytics.order_fact;

SELECT
    COUNT(*) AS rows,
    COUNT(DISTINCT customer_unique_id) AS unique_customers,
    COUNT(*) FILTER (WHERE is_repeat_customer) AS repeat_customers,
    SUM(total_item_revenue) AS item_revenue
FROM analytics.customer_features;

SELECT
    seller_id,
    seller_order_count,
    review_count,
    average_review_score,
    late_delivery_rate,
    low_review_rate
FROM analytics.seller_performance
WHERE review_count >= 20
ORDER BY average_review_score;
```
